# ЮKassa: платная генерация после бесплатного лимита

Выбранный пользователем провайдер — ЮKassa, валюта RUB. Цена не задана и не придумана приложением. До её подтверждения и проверки магазина модуль отключён: PAYMENTS_ENABLED=false. Никакие реальные платежи/вызовы генератора при разработке не выполнялись.

## Поведение

Новый аккаунт получает credits=2 и paid_credits=0. Сначала расходуются бесплатные попытки, затем оплаченные. Если оба баланса равны нулю, API возвращает 402 PAYMENT_REQUIRED, кабинет предлагает приобрести одну дополнительную генерацию. Если оплата не подключена, кнопка недоступна и интерфейс прямо сообщает об этом.

Цена — только серверная PAID_GENERATION_PRICE_KOPEKS, положительное целое число копеек. Клиент не задаёт сумму или количество начислений. Создание платежа происходит через POST /api/billing/checkout, с авторизацией JWT и UUID Idempotency-Key. Повторный запрос использует ту же запись billing_orders и тот же ключ идемпотентности ЮKassa. Данные карты в Velora AI не передаются: пользователь переходит на защищённую страницу провайдера.

Webhook POST /api/billing/webhook принимает уведомление payment.succeeded, но не доверяет его содержимому. Сервер заново получает платёж через собственную авторизацию GET https://api.yookassa.ru/v3/payments/{id}, проверяет статус succeeded, paid=true, сумму, RUB, test/live-режим и привязку metadata к локальному заказу. В транзакции блокируется заказ и единожды добавляется paid_credits=paid_credits+1. Поддельный JSON, URL возврата и дубликаты уведомлений не дают баланс.

После возврата /?payment=return кабинет сверяет сохранённый заказ через POST /api/billing/reconcile; это восстанавливает начисление и при потерянном уведомлении. Запрос ограничен собственными заказами пользователя, по той же проверке API и с защитой от двойного начисления. При задержке можно обновить баланс кнопкой кабинета. Ни reconcile, ни возврат пользователя не создают новый платёж.

Все деньги считаются целыми копейками, без округления float. Минимально допустимую сумму и реальные способы оплаты дополнительно проверяет ЮKassa. Цена в тестах 123.45 RUB — фикстура, не тариф сайта.

## Секреты и конфигурация

При включении требуется явное PAYMENT_PROVIDER=yookassa, PAYMENTS_MODE=test или live, PAID_GENERATION_PRICE_KOPEKS, HTTPS PUBLIC_APP_URL без credentials/query/path, YOOKASSA_SHOP_ID и YOOKASSA_SECRET_KEY. Секреты читаются только сервером, не выдаются через API и не коммитятся. Обычный запуск с выключенным модулем этих значений не требует. HTTP-клиент имеет таймаут, сохраняет TLS-проверку и отклоняет перенаправления API, чтобы не передавать авторизацию на другой хост.

Для GET/POST API ЮKassa нужен доступ к api.yookassa.ru и серверная авторизация магазина. В текущем процессе YOOKASSA_SHOP_ID и YOOKASSA_SECRET_KEY отсутствуют. Никаких изменений настроек сетевых секретов для их получения не выполнялось. Basic-авторизация требует пригодного для SDK значения в серверном процессе; существование HTTPS proxy-secret само по себе не доказывает, что это значение доступно для Basic-auth.

Страница оплаты ограничена HTTPS-хостами yoomoney.ru/yookassa.ru. PAYMENTS_MODE=test маркируется в кабинете как тестовый режим. Production с включённой генерацией и тестовой оплатой запускаться не должен: проверка конфигурации запрещает такое сочетание. Предварительная выкладка допускает выключенные реальные генерации/платежи.

## Изменения БД

Только в локальной тестовой базе применены аддитивные изменения:

- users.paid_credits — отдельный оплаченный баланс, DEFAULT 0;
- billing_orders — журнал заказов и однократного начисления;
- generation_receipts — результат и hash запроса для повторов с тем же Idempotency-Key.

Исходные credits и пользовательские записи не сбрасываются. Миграция транзакционная и сериализована advisory-lock, чтобы несколько экземпляров не создавали таблицы одновременно. В рабочую БД ничего не применено. Перед рабочей миграцией нужна подтверждённая копия Render и отдельное разрешение.

## Что проверено и ограничения

Проверены настоящая локальная PostgreSQL, имитатор API ЮKassa и браузерный сценарий: 2 бесплатных → оплата → подтверждённая оплаченная попытка → генерация. Проверены дубликаты/подделка уведомления, чужой заказ, ошибочная сумма, сбой API, восстановление потерянного уведомления, конкурирующие списания и откат при обычной ошибке генерации.

Для генерации с тем же Idempotency-Key и тем же входом успешный сохранённый результат возвращается повторно без нового вызова провайдера/списания. Другой вход с использованным ключом даёт 409. Это покрывает потерю HTTP-ответа после COMMIT; сбой процесса/соединения между выполнением провайдером и фиксацией БД всё ещё требует сверки задания. Код без переданного ключа сохраняет совместимость со старым API, но не получает защиты от повторной отправки.

Возвраты платежей, спорные операции и кабинет администратора пока не автоматизированы. Провайдерские кассовые настройки/чеки и реальные callbacks не проверены. До коммерческого запуска необходимы тестовый проход в настоящем магазине и решение этих эксплуатационных вопросов. Не считать модуль готовым к приёму реальных денег только на основании тестов с имитатором.
